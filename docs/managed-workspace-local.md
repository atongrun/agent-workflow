# Managed workspace local implementation slice

This candidate adds an existing-repository flow without upgrading Pi 1.1.0 or adding an agent scheduler. It is not deployed, and Windows runtime acceptance is outstanding.

Pi native RPC, session and extension tool dispatch remain the authorities for model behavior. `awf_repository` is one trusted extension tool over an immutable bounded source bundle. The existing Worker resolves that bundle using its existing `GITHUB_READ_TOKEN`; no credential is copied to the Host or executor. A planning read creates no Git clone, worktree, branch or execution request. Repository text is untrusted data. Files omitted by the bundle are explicitly unknown, not silently available. The initial bundle includes at most 32 text files and 96 KiB (admission accepts at most 128 KiB); on-demand fixed-SHA browsing is implemented through the authenticated Worker reader described below.

Confirmation stores the exact plan content/hash/revision, target revision, repository ID/name, node/project, branch and fixed base ref/SHA. Start checks that snapshot and dispatch uses it, rather than reconstructing an execution from mutable task state. Existing nil/absent optional fields preserve old request/job JSON fingerprints. Target changes clear confirmation. No Git plan commit or push is required.

A node may configure an existing absolute `managedRoot` once. Its authenticated project catalog advertises a reserved `managed` capability; the Host does not need a matching checkout. The node's existing serial execution slot prepares `<root>/repos/<repositoryId>` and `<root>/tasks/<taskId>` only after Start. The managed branch is `awf/<taskId>`. A create-only task ownership record binds repository, branch and base SHA. Clone is installed from a temporary directory; retries inspect actual Git state. Existing dirty first-run worktrees, foreign remotes/worktrees, escaped or linked directories and ownership conflicts stop without reset/clean. Rework preserves the original task/session and existing changes.

Git preparation is a small machine-local adapter to the existing Git executable. The concrete gap is root-contained, task-owned directory resolution and deterministic Git state verification across the native OpenCode boundary; neither Pi's RPC/session lifecycle nor a free-form model response supplies those facts. Go retains the existing authenticated machine/process boundary only. No new scheduling/checkpoint/model loop or parallel execution ledger is introduced.

Every native session, status, message, event stream, question, cancellation and recovery operation uses the persisted job workspace. Managed-root changes cannot relocate existing task directories. Existing fixed projects remain supported without migration. The managed execution prompt explicitly prohibits remote repository creation, credential changes, push, merge and deploy in this local slice. This instruction and the existing native permission handling are not a new OS/network sandbox; production enablement must retain the executor’s actual permission boundary. The current product still requires remote-SHA evidence for Done, so local implementation success does not silently become remotely delivered Done.

Tests use synthetic Git repositories and native HTTP/SSE fixtures. They do not establish production Git authentication, Windows behavior or actual native model acceptance. Cross-OS task identifiers and HTTPS/SSH remote canonicalization are tested locally. Future slices may add advanced directory overrides, separately authorized delivery policy and repository creation; those are not claimed by this candidate.

## On-demand source reader and confirmation gate

The initial bundle is only a cache/preview, not evidence of a complete repository inspection. `awf_repository` supports fixed-SHA `read`/`list` operations and a bounded `cursor`. The Worker resolves the repo and SHA from the saved task, not the caller. Directory pages contain at most 200 entries; file pages contain at most 200 lines and 64 KiB, with an explicit next cursor. Files above 1 MiB, binary files, links, excluded sensitive configuration and entries absent from the verified tree remain unavailable. Common source languages and executable source file modes are supported.

The Host's operator-controlled `AWF_REPOSITORY_READ_URL` must point exactly to `/api/awf/repository-read` on an authorized HTTPS origin (HTTP loopback is allowed for fixtures). This introduces no new repository secret: the narrow read route authenticates the existing Host bearer and reads GitHub using the existing Worker read token. Existing Access service credentials may be reused via `AWF_ACCESS_CLIENT_ID`/`AWF_ACCESS_CLIENT_SECRET`; no production credentials or Access policy are created or expanded by this candidate. Actual Host-to-Worker Access eligibility is unverified and must not be assumed.

A truncated source cannot be confirmed until a bound on-demand list request succeeds with a complete upstream tree. Missing access, denial, mismatched identity/path, a changed target or a truncated upstream catalog fail without admitting a confirmation receipt. The approval records successful reader verification. Older approvals lacking that verification cannot start a truncated-source execution. Exact confirmed-request retries reuse the original receipt without another external read. The preflight runs outside the store update lock because the Worker independently reads the task back through Host GET. Source text is still untrusted data, and the availability probe does not prove Pi inspected every relevant file or that its plan is correct; semantic review remains Pi's and the user's responsibility.

The narrow machine route does not relax browser mutation Origin checking. Source reads are GET-only upstream and never reserve execution, clone, create repositories, write credentials, push or deploy.

## Updater fixture regression

The pre-existing `TestUpdateProgressWiringAndStdout` failed on arm64 because production `updateWithProgress` selects `runtime.GOARCH`, while `freshFixtureClient` advertised only amd64 assets. The test fixture now accepts an explicit architecture; the update progress test uses its runtime architecture and the native activation fixture also supplies the matching architecture. Existing installation fixtures continue using their deliberate amd64 stub. `TestUpdaterFixtureStagesBothSupportedArchitectures` verifies metadata, download, checksum and staging for amd64 and arm64 without executing a downloaded binary. Existing progress, hash-failure, executable-check and stdout assertions remain intact. No production updater selection code changed.

## Verification boundary

Full Go tests pass on the local Mac with synthetic fixtures. Worker/target tests cover wrong bearer, caller-selected repo/SHA, stale/deleted tasks, traversal, sensitive paths, symlink denial, pagination, source tampering, exact receipt replay and browser Origin boundaries. This is local contract verification, not production Access/Git authentication or actual Windows/model acceptance. No independent reviewer verdict is implied by these checks; the patches are prepared for a separate review.

## Independent review closure

A separate read-only reviewer inspected the latest candidate and reported no remaining blocking finding after three P2 issues were fixed: incomplete/mistyped reader responses now fail strict schema and pagination validation; supplied sensitive source files are rejected by both Worker and Host (including case variants such as `.ENV.json`); and confirmation admission rechecks the task lifecycle as well as target revision and SHA, preventing a delete/restore from reusing an old preflight. Added negative tests cover each issue.

The reviewer independently ran focused Worker, Host bridge/lifecycle/sensitive-path, and real-Git node idempotency/dirty-tree/remote/path tests. Current relevant Worker/Dash coverage is 258 passing tests. Host boundary tests pass with the race detector. Full Go coverage passed before these review fixes; the changed Host package was then rerun in full with vet. Production Access/Git authorization, native Windows execution and real Pi/OpenCode model acceptance remain outside this local validation.
