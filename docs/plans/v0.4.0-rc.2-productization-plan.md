Status: **Frozen for the next implementation session; release remains separately authorized**

Review baseline: `origin/main` at `1851dd84c7ef6a74b2fb25939eb6aac505c19f90`

Reviewed on: 2026-08-24

## 1. Product decision

RC.2 is a productization release, not an execution-model expansion. The current serial authority
model remains frozen:

```text
Install AWF
  -> awf init
  -> Machine Ready
  -> Human + Agent discuss a Plan
  -> Human approves and commits the Plan
  -> Human authorizes an Agent to use AWF
  -> Agent invokes AWF
  -> Architect
  -> Coder
  -> Reviewer
  -> CI
  -> trusted merge
  -> read latest main
  -> next TaskCard
  -> MILESTONE_COMPLETE / BLOCKED
```

The release objective is to make this path understandable, installable, operable, observable and
debuggable for an external user whose Agent Bus and selected Agent Tools are already installed and
authenticated.

The execution semantics that remain frozen include exact SHA and Git/PR provenance, one active card,
fresh-main sequencing, independent review, CI and merge authority, no automatic replay after an
ambiguous provider outcome, durable evidence, handler-success before ACK, and Agent Bus as
transport-only.

## 2. Current-code review conclusions

### 2.1 Operations package boundary

**Finding: real structural debt, not a current RC.2 Golden Path blocker.**

Current main force-includes `scripts/` into the wheel as `agent_workflow/operations`, locates it with
`agent_workflow.resources.operations_dir()`, prepends that directory to `sys.path`, and imports
top-level modules such as `awf_plan` and `awf_role`. The same import shape is asserted by
`tests/verify_installed_wheel.py`.

The 2026-08-24 review built the main wheel and ran the repository's installed-wheel verifier from a
new venv and a cwd outside the source checkout. It passed. The wheel contained the operations
scripts, provider adapters, model-bin assets, service assets, schemas and templates. Therefore the
current product does not depend on a source-checkout `scripts/` directory.

The remaining risk is Python module identity and import collision, not missing wheel content. A
formal package migration touches CLI imports, node/status loaders, listener script entry, internal
absolute imports, the lazy `awf_role -> awf_plan` edge, model-bin path handling, test fixtures and
installed-wheel assertions. That is a broad physical migration with little immediate user benefit.

**Decision:** defer `scripts/ -> src/agent_workflow/operations/` to immediate post-RC.2. Keep it a
physical/package-boundary cleanup with behavior-conformance tests. Do not combine it with business
refactoring or `awf_role.py` decomposition.

### 2.2 `awf_role.py`

**Finding: frozen legacy core, not an RC.2 blocker.**

`scripts/awf_role.py` is 5,099 lines, but current main already delegates provider argv rendering to
`scripts/agent_adapters/`, process execution to `awf_executor.py`, TaskCard postflight and report
semantics to installed Runtime artifact helpers, and selected Runtime v2 boundaries to
`src/agent_workflow/runtime/`.

No reviewed Golden Path call requires decomposition before it can install, initialize, dispatch,
review, merge or stop safely. File size and SRP alone are not release evidence.

**Decision:** freeze it. RC.2 may make only import-path adjustments required by an accepted package
change, a demonstrated bug fix, logging, or user-facing error projection. No feature, provider
framework, recovery redesign or aesthetic refactor is allowed.

### 2.3 Crash and recovery

**Finding: fail-closed semantics are present; user projection and live acceptance are incomplete.**

Coder and Reviewer handlers persist monotonic recovery checkpoints and refuse a second model
invocation after an ambiguous `model_started` boundary. A same-delivery result may continue only
when exact durable zero-exit/process/workspace evidence proves it. The test suite covers these
boundaries.

The accepted Phase 5-03 milestone also retained a real Coder process-exit run: Card 2's duplicate
delivery reached the ambiguous-model no-replay gate and terminal-failed naturally, with no manual
ACK, requeue, replay or evidence rewrite. This proves safe stop, not automatic resume.

The product gap is that bare `awf status` combines a high-level PlanRun line set with per-role status
but does not consistently project the exact failed side effect, one blocker and one safe next action.
The PlanRun can remain `card_active` while the underlying delivery has terminal-failed. A user should
not need to infer that join or inspect/edit `run.json`, a checkpoint or an authority file.

**Decision:** RC.2 must add read-only projection and run two live kill acceptances. It does not add
provider-session restoration or general automatic resume. If E2E proves that a normal provider exit
cannot be ended without editing internal state, Phase 5 may add one minimal durable-boundary
terminalization/recovery action; otherwise it stops at honest diagnostics and a documented fresh-run
procedure.

### 2.4 TaskCard machine truth

**Finding: one production artifact authority exists, but Plan-specific parsing is duplicated. No
current legal-card contradiction was demonstrated.**

The Runtime artifact module is authoritative for report paths, allowed paths, postflight commands,
ReviewReport normalization and role-side validation. `awf_role.py` delegates those operations to the
installed Runtime boundary. `scripts/awf_taskcard.py` separately parses role selection, while
`plan_loop.validate_taskcard_binding()` and `runtime.architect._validated_taskcard()` each validate a
Plan-specific subset before persistence and dispatch.

The reviewed valid Plan cards pass all stages, and the Phase 5 two-card milestone is real evidence.
The partial validators can, however, accept an early subset and reject additional invalid semantics
later. That is fail-closed but produces avoidable late failure and invites future regex drift.

Main still asks Pi for complete Markdown TaskCards. The closed seven-field semantic JSON plus trusted
TaskCard assembler exists only on the unmerged `r4-final-candidate` branch and has not completed its
formal R4 acceptance. It is not current main truth and must not be documented or released as proven
support.

**Decision:** RC.2 adds a shared conformance corpus and closes only demonstrated parser drift. It
also tightens the Architect decomposition policy. It does not adopt TaskCard vNext, change the
Markdown artifact, relax validators, merge unaccepted provider support, or add another parser.

### 2.5 Product prototype DoD reachability

The current code already proves the hard execution core: an installed wheel, exact managed
listeners, a real two-card serial milestone, Human-free TaskCard authoring, exact review/CI/merge,
fresh-main continuation and terminal `MILESTONE_COMPLETE`.

The remaining product blockers are narrow:

1. default status/error output is not yet one coherent product projection;
2. normal help and architecture documentation still expose or describe conflicting product shapes;
3. configured role selections are not always reused by Plan start, leaving avoidable Agent-facing
   parameters;
4. RC.2 still needs clean-installed live E2E, including blocked status, Coder/Reviewer kill boundaries
   and Windows/macOS managed-listener UX.

### A. Agent-native / MCP facade

- **Current AWF capability:** an authorized Agent can invoke `awf plan start`; the function delegates
  to the existing Plan facade and workflow authority.
- **Actual gap:** the Agent must know CLI flags, and there is no structured machine response shared
  with status.
- **Product benefit:** a Human can say “use AWF” while the initiating Agent calls a stable tool.
- **Golden Path impact:** improves entry ergonomics but does not currently block the path because
  Codex/Pi/OpenCode initiating Agents can execute the CLI.
- **Implementation cost/risk:** an MCP server adds protocol lifecycle, dependency, schema, packaging
  and security surface before the operations package and status contracts are stable.
- **Authority/security impact:** acceptable only if the adapter owns no state, merge, TaskCard,
  recovery or Agent Bus transport authority.
- **Recommendation:** **immediate post-RC.2**.
- **Minimal viable shape:** stdio server; `start_plan` and `get_status` only; call installed AWF
  application/facade functions; return the same `current_state`, `blocker`, `next_safe_action` and
  `allowed_actions` contract as CLI status. Consider `doctor` and `stop` only after those two tools
  pass a real Human authorization -> Agent tool call -> existing workflow acceptance.

### B. Architect / TaskCard decomposition discipline

- **Current AWF capability:** one card at a time, no pre-generated queue, fresh main after each merge,
  self-contained TaskCard structure and frozen Plan facts.
- **Actual gap:** the Architect prompt is precise about protocol syntax but not explicit enough about
  PR-level granularity, zero-chat-context execution and leaving tactical decisions to Coder.
- **Product benefit:** fewer over-broad or over-designed cards and less invalid downstream work.
- **Golden Path impact:** directly affects Architect reliability.
- **Implementation cost/risk:** low; prompt/policy and focused tests only.
- **Authority/security impact:** none; Plan scope and validators remain authoritative.
- **Recommendation:** **RC.2**.
- **Minimal viable shape:** add exactly the bounded policy from this plan to initial and next-card
  contexts; no schema field or planner framework.

### C. Explicit `allowed_actions` / next-safe-action projection

- **Current AWF capability:** PlanRun status, `DecisionOutcome`, lifecycle facts, checkpoints,
  blockers and several `next_action`/`next_legal_action` values already exist.
- **Actual gap:** the values are split across PlanRun, legacy ledger, Runtime v2 and node status, and
  default output does not produce one product answer.
- **Product benefit:** Humans and initiating Agents stop guessing after failure.
- **Golden Path impact:** directly closes observability and debuggability DoD.
- **Implementation cost/risk:** medium; joining facts incorrectly could claim an unsafe action.
- **Authority/security impact:** read-only and conservative; unknown/conflicting facts must project
  only inspection/stop, never mutation.
- **Recommendation:** **RC.2**.
- **Minimal viable shape:** `current_state`, `current_card`, `last_completion`, `blocker`,
  `next_safe_action`, `allowed_actions`; one shared pure projection used by human and JSON status.

### D. Provider-native session resume

- **Current AWF capability:** artifact/checkpoint recovery and no-replay semantics; no session-history
  authority.
- **Actual gap:** restarting a provider UI/session may save context, but exact session identity is not
  a current durable Workflow fact.
- **Product benefit:** lower recovery latency when safely bound.
- **Golden Path impact:** not required for safe stop and fresh-run recovery.
- **Implementation cost/risk:** high ambiguity and provider-specific behavior. agtx currently uses
  commands such as `codex resume --last` and generic `--continue`, which are too weak for AWF
  authority.
- **Authority/security impact:** unacceptable unless an exact provider session ID is durably bound
  and remains only an optimization over artifact truth.
- **Recommendation:** **backlog**.
- **Minimal viable shape if later adopted:** exact provider session identity plus workspace/run/
  invocation binding; never `--last`; artifacts and trusted external facts remain authoritative.

### E. Benchmark / evaluation harness

- **Current AWF capability:** real dogfood reports already record card count, invocations, rework,
  exact review/CI/merge and failure evidence.
- **Actual gap:** no normalized cross-run result file for completion rate, first-pass review, model
  usage, wall time or wrong-head prevention.
- **Product benefit:** release comparisons and regression detection.
- **Golden Path impact:** not an RC.2 functional blocker.
- **Implementation cost/risk:** medium to high if it becomes a new infrastructure project.
- **Authority/security impact:** evidence-only; benchmark output must not become Workflow authority.
- **Recommendation:** **immediate post-RC.2**.
- **Minimal viable shape:** first normalize existing dogfood evidence; later add disposable fixtures
  for completion, review/rework, cost/time and wrong-head/wrong-merge safety. No benchmark platform in
  RC.2.

### F. First-run / auto-detection philosophy

- **Current AWF capability:** detects Git and authenticated `gh`, Git root, remote repository slugs,
  Agent Bus client capability, configured Bus URL/tokens, tool executables/versions, role defaults,
  managed lifecycle and exact listener connectivity.
- **Actual gap:** provider authentication is assumed rather than observed; Plan start can still need
  coder/reviewer overrides even when a compatible local machine binding already exists; output does
  not clearly distinguish “installed/version observed” from “authentication assumed”.
- **Product benefit:** fewer internal parameters and more honest first-run diagnostics.
- **Golden Path impact:** directly affects init and Agent invocation.
- **Implementation cost/risk:** low if limited to existing facts and configured bindings; high if it
  becomes discovery/configuration infrastructure.
- **Authority/security impact:** inferred values must be shown and frozen into the existing PlanRun/
  TaskCard authority before dispatch.
- **Recommendation:** **RC.2**.
- **Minimal viable shape:** infer remotes and supported role selections from existing machine config;
  preserve explicit overrides; label provider auth as a prerequisite unless a stable credential-safe
  probe already exists; do not create a registry or remote profile-discovery service.

## 4. RC.2 Definition of Done

RC.2 may be tagged only when all of the following are true from a clean installed build:

1. README explains AWF in about 30 seconds and architecture/help agree with current code.
2. Default Human vocabulary is `awf init`, execute an approved Plan, `awf status`, `awf stop` and
   `awf doctor`.
3. The wheel runs outside a source checkout and requires no source-tree `scripts/` path.
4. `awf init` prints `Ready` only after exact configured/installed/running/connected/listener facts;
   failures print one blocker and one next safe action.
5. An approved committed Plan completes Architect -> Coder -> Reviewer -> CI -> merge -> fresh-main
   next card.
6. The Human writes no TaskCard and coordinates no internal delivery/ACK/checkpoint operation.
7. The initiating Agent does not need to reconstruct role selections already present in supported
   project/machine configuration.
8. Bare `awf status` answers state, current card, last completion, blocker and next safe action;
   `--explain` shows the detailed causal/internal facts.
9. Default errors answer what happened, why AWF stopped and what is safe next.
10. One clean-installed real milestone completes at least two cards.
11. Coder and Reviewer mid-run kill acceptances prove safe stop, visible side effects and a
    documented next action without manual internal-state edits.
12. Exact SHA, credential isolation, independent Reviewer, CI and trusted merge authority remain
    unchanged.
13. Managed listeners on Windows and macOS do not create periodic visible console popups or leave
    unexplained process/worktree state after exact stop.

Agent Bus and selected Agent Tools may be assumed installed and authenticated. An offline/no-Bus
single-file demo is not required.

## 5. Frozen implementation phases

Every phase stops at its exit criteria. A green build is evidence, not authorization to expand scope.

### Phase 0 - Scope freeze

- **Problem:** repeated reviews can reopen architecture and grow RC.2.
- **Evidence from current code:** the execution loop is already proven; remaining gaps are product
  projection and acceptance.
- **Golden Path impact:** prevents work from drifting away from external-user blockers.
- **Exact scope:** adopt this plan, its DoD, agtx decisions, blockers, backlog and non-goals as the
  sole RC.2 authority.
- **Non-goals:** implementation, release, provider expansion, Runtime default migration.
- **Files/modules likely affected:** this plan and `HANDOFF.md` only.
- **Verification:** links resolve; baseline/ref/release facts match live Git/GitHub.
- **Exit criteria:** owner accepts this plan; no competing RC.2 plan is authoritative.
- **Risk:** low; stale baseline facts must be refreshed before implementation.

### Phase 1 - Product surface and first-run truth

- **Problem:** README is product-oriented, but `docs/architecture.md` still describes only a thin
  validation CLI; top-level help exposes many internal/compatibility commands; Plan start can require
  values already inferable from supported configuration.
- **Evidence from current code:** `cli.main()` registers setup/dispatch/preflight/feedback/resume and
  node internals beside normal commands; `facade.discover_machine_capabilities()` already detects
  most first-run facts; `plan start` still owns explicit coder/reviewer defaults and overrides.
- **Golden Path impact:** new users receive conflicting mental models and initiating Agents must know
  unnecessary flags.
- **Exact scope:** align README, architecture, release-support claims and help; foreground only normal
  commands; retain internal commands as compatibility/support surfaces; reuse supported configured
  role selections and inferred Git remotes where deterministic; make Ready/auth assumptions honest.
- **Non-goals:** delete compatibility commands, new configuration framework, remote role registry,
  new provider, tool-specific login manager, MCP.
- **Files/modules likely affected:** `README.md`, `docs/architecture.md`, `src/agent_workflow/cli.py`,
  `src/agent_workflow/facade.py`, focused CLI/facade tests.
- **Verification:** help snapshots, init capability fixtures, explicit-override precedence, docs/code
  provider table comparison, credential-safe error tests.
- **Exit criteria:** a new user sees one Golden Path; existing support commands still work; inferred
  selections are displayed and frozen into existing authority.
- **Risk:** medium; never infer a provider/model that cannot be proven from existing config.

### Phase 2 - Unified status, errors and allowed actions

- **Problem:** status facts are split and default output can leave a Plan card active while its
  delivery is failed, without one clear next action.
- **Evidence from current code:** `plan_status_lines()`, `status.snapshot()`, node lifecycle and legacy
  run status each render separate views; Plan lines omit next action; detailed causal facts appear
  only under role/run-specific paths.
- **Golden Path impact:** this is the main RC.2 observability/debuggability blocker.
- **Exact scope:** implement one pure read-only projection over existing facts; render concise Human
  output and a stable JSON form; include state/current card/last completion/role readiness/Bus and
  listener state/blocker/next safe action/allowed actions; project errors at CLI/facade boundary with
  `--explain` for detail.
- **Non-goals:** new state machine, state mutation from status, automatic recovery, ACK/requeue,
  dashboard/TUI, Runtime v2 default switch.
- **Files/modules likely affected:** `src/agent_workflow/status.py`, `facade.py`, `plan_loop.py`,
  `cli.py`, status/facade/plan tests.
- **Verification:** table-driven projections for running, blocked, terminal, missing/contradictory
  facts, merge ambiguity, failed provider and safe stop; prove status is byte-for-byte state
  non-mutating.
- **Exit criteria:** bare status answers the five required user questions; unknown facts never produce
  a mutating action; Human and JSON views share semantics.
- **Risk:** high if joins overclaim authority; conflict must collapse to inspect/stop.

### Phase 3 - TaskCard discipline and contract conformance

- **Problem:** TaskCard syntax/semantics are validated in several stage-specific readers and the
  Architect prompt does not fully state the PR-level decomposition policy.
- **Evidence from current code:** Plan binding, Architect persistence, role selection and Runtime
  postflight use overlapping regex/JSON logic, while role-side postflight/report validation already
  delegates to Runtime.
- **Golden Path impact:** late invalid-card stops and over-broad cards reduce the normal loop's
  reliability.
- **Exact scope:** add one valid/invalid TaskCard conformance corpus across every production read path;
  reuse installed semantic helpers where a mismatch is demonstrated; add the bounded one-card/
  self-contained/no-chat/no-future-card/no-tactical-micromanagement policy to initial and next-card
  prompts.
- **Non-goals:** TaskCard vNext, schema expansion, Structured Output project, validator relaxation,
  prompt retry, pre-generated queue, unaccepted R4/provider changes.
- **Files/modules likely affected:** `src/agent_workflow/plan_loop.py`,
  `runtime/architect.py`, `runtime/artifact.py`, `scripts/awf_taskcard.py`, `scripts/awf_plan.py`,
  conformance tests and architecture text.
- **Verification:** same corpus receives the same semantic verdict at every applicable stage; existing
  real-card fixtures remain accepted; prompts contain policy without changing frozen facts.
- **Exit criteria:** no demonstrated legal-card disagreement and no new parser; machine semantics and
  Markdown artifact relationship are documented honestly.
- **Risk:** medium; preserve legacy-card compatibility only where it is still a current user path.

### Phase 4 - Clean installed-product E2E

- **Problem:** local/unit evidence cannot prove RC.2 product behavior across install, lifecycle,
  distributed roles and crash boundaries.
- **Evidence from current code:** RC.1 has a real two-card milestone and installed-wheel proof, but
  not the combined RC.2 status/first-run/kill/Windows-console acceptance.
- **Golden Path impact:** this is the release acceptance gate.
- **Exact scope:** fresh wheel install; version; init; managed listener lifecycle; Bus connectivity;
  real Architect/Coder/Reviewer; at least two serial cards; exact review/CI/merge; status while
  running/blocked/complete; stop; Windows/macOS UX; one fresh Coder kill and one fresh Reviewer kill.
- **Non-goals:** reuse retained deliveries, manual ACK/requeue/resend, synthetic business PASS, full
  recovery matrix, new provider acceptance, release publication.
- **Files/modules likely affected:** acceptance docs/fixtures only unless a Golden Path blocker is
  found.
- **Verification:** fresh branch/run/delivery identities, exact Git/GitHub facts, handler-success and
  ACK evidence, scoped queues, installed paths, process/listener observations, preserved failures.
- **Exit criteria:** every DoD item has direct evidence; both kill runs stop safely and require no
  internal-state edits; failed identities remain failed.
- **Risk:** high operationally; run serially and fail closed at the first real boundary.

### Phase 5 - Only Golden Path blockers and release closeout

- **Problem:** E2E may reveal one narrow blocker that cannot be predicted safely from static review.
- **Evidence from current code:** the execution path is mature; broad architecture work would create
  more risk than it removes.
- **Golden Path impact:** repairs only objective DoD failures.
- **Exact scope:** one bounded fix per demonstrated blocker, focused tests, fresh acceptance, truthful
  docs and release notes; prepare but do not publish the release without owner authorization.
- **Non-goals:** “while here” refactors, operations package migration, `awf_role` split, MCP, provider
  session resume, new provider, benchmark platform, DAG/parallel work, dashboard/TUI.
- **Files/modules likely affected:** only the minimal boundary named by each retained failure.
- **Verification:** focused regression, relevant CI, independent review for L2/L3 changes, fresh E2E
  identity; retain failed evidence.
- **Exit criteria:** all DoD items pass, no true blocker remains, main/docs/release claims agree, and
  owner has a release-ready exact SHA.
- **Risk:** scope creep; any proposal must name the exact Golden Path step it blocks.

## 6. True release blockers

Only these are blockers for tagging RC.2:

1. unified status/error/next-safe-action projection is not implemented and accepted;
2. product/help/architecture claims are not reconciled with code;
3. clean-installed two-card and Coder/Reviewer kill E2E has not passed on the RC.2 candidate;
4. Windows/macOS managed-listener UX has not been accepted on the candidate;
5. any E2E failure that requires manual editing of `run.json`, checkpoint or authority state to end
   a normal failed run.

Operations package cleanup, `awf_role.py` decomposition, MCP, provider session resume, benchmark
infrastructure and new provider support are not RC.2 blockers.

## 7. Immediate post-RC.2

1. **Operations formal package:** move production Python modules under
   `agent_workflow.operations`, remove runtime `sys.path` mutation, preserve script/service assets and
   lazy import behavior, and rerun the installed-wheel/cross-platform conformance suite.

   and status contracts; prove one real Human authorization -> Agent tool call -> current Workflow.
3. **Light evaluation:** normalize existing dogfood metrics before considering a broader benchmark
   harness.
