Status: **Frozen for implementation; release remains separately authorized**

Review baseline: `origin/main` at `58b3d0ca160533de9a9360cbf9b63636259fef03`

Frozen on: 2026-08-24

## 1. Product contract

Agent Workflow is not a generic multi-agent scheduler. It turns one Human-approved, committed Plan
into a serial, distributed and evidence-gated delivery loop:

```text
Install AWF
  -> initialize one project and its participating machines
  -> Human + initiating Agent discuss a Markdown Plan
  -> Human approves and commits the Plan
  -> Human tells the Agent to use AWF
  -> Agent calls the AWF tool facade
  -> Architect
  -> Coder
  -> Reviewer
  -> CI
  -> trusted merge
  -> read exact latest main
  -> next TaskCard
  -> MILESTONE_COMPLETE / BLOCKED
```

The first external user is one technical owner who controls the repository, Agent Bus, participating
machines and Agent Tool accounts. Team membership, separate owners, delegated credentials and
organization approval policy are later product work.

### 1.1 Human and Agent surfaces

The Human-facing vocabulary is deliberately small:

```text
install
initialize
approve a Plan
ask an Agent to execute it
ask what is happening
ask AWF to stop or deinitialize
```

The normal Human instruction is:

> This Plan is approved and committed. Use AWF to complete it.

The initiating Agent calls MCP tools internally. The Human does not need to know tool names or CLI
parameters. `awf plan start ...` remains the installed application contract, debugging surface and
compatibility entry, not the permanent product interaction.

### 1.2 Authorization

One PlanRun is authorized by the conjunction of:

```text
exact committed Markdown Plan
+ explicit Human instruction to use AWF
+ initiating Agent start_plan tool call
= PlanRun execution authorization
```

The Plan remains ordinary Markdown. RC.2 adds no Plan schema, `approved: true` marker, approver
database, signature or workflow frontmatter. Git blob identity is the immutable scope fact; the
Human instruction plus tool call is the operation authorization fact.

### 1.3 Frozen execution semantics

RC.2 preserves:

- exactly one active TaskCard per PlanRun;
- latest-main sequencing between cards;
- exact Plan/TaskCard/profile/tool/model/workspace/Git/PR identity;
- independent Reviewer verdict, required CI and trusted merge;
- credential-free artifacts and model workspaces without merge credentials;
- durable checkpoint/outbox/inbox and CompletedCardFact evidence;
- handler-success before transport ACK;
- no automatic replay after an ambiguous provider invocation or external effect;
- Agent Bus as transport-only;
- read-only status;
- failed and ambiguous identities retained rather than rewritten as PASS.

Roles remain exactly Architect, Coder and Reviewer. RC.2 makes Provider selection configurable; it
does not permit dynamic role creation, online-agent routing, silent fallback or mid-run provider
switching.

## 2. Project topology and configuration

### 2.1 Tracked project truth

RC.2 adds one credential-free tracked file:

```text
.awf/project.yaml
```

Minimal shape:

```yaml
apiVersion: agent-workflow/v1
kind: Project

repository:
  baseRef: main

topology:
  name: role-specialized

roles:
  architect:
    agent: architect
    tool: pi
    model: tool-default
  coder:
    agent: coder
    tool: opencode
    model: tool-default
  reviewer:
    agent: reviewer
    tool: codex
    model: tool-default
```

It may contain logical Agent Bus identities, Agent Tool choice and opaque tool-native model refs. It
must not contain Bus URLs/tokens, credentials, host/IP names, absolute local paths, workspace paths,
profile snapshots, process/session IDs or listener state.

The file is created or updated through AWF; a Human need not hand-write YAML. It is committed before
Plan execution. Machine-local bindings live in platform configuration, keyed to exact repository
identity; a compatibility reader may consume the current repository-local `.awf/machine.json`, but
new normal setup must not require committing machine-local state.

### 2.2 Discovery boundary

`awf init` discovers only facts local to the current machine:

- Git root, remotes and authenticated GitHub CLI;
- Agent Bus client/configuration and required role token presence;
- installed Pi/OpenCode/Codex executables and versions;
- selected local roles, native lifecycle, profile, workspace and listener readiness.

RC.2 does not create an online cross-machine role registry. Agent Bus queue/connection presence is
not Workflow authority and must not choose whichever provider happens to be online. The project
topology declares intended logical roles; local profiles bind machines to those roles; Deep
Preflight proves the exact routes before dispatch.

### 2.3 Selection and override

Project topology provides defaults. A Human may explicitly request a different tool/model before a
PlanRun starts. The initiating Agent may pass that exact override, which AWF displays and freezes in
the PlanRun and TaskCard.

No project-file or online-state change affects an active PlanRun. Changing topology requires a
Human-confirmed project-file commit, affected-machine init/upgrade, doctor readiness and a new
PlanRun.

### 2.4 Official topology profiles

RC.2 ships and accepts two official profiles:

```text
uniform-opencode (Quick Start / lowest operational friction)
OpenCode Architect -> OpenCode Coder -> OpenCode Reviewer
```

```text
role-specialized (recommended for normal delivery)
Pi Architect -> OpenCode Coder -> Codex Reviewer
```

The uniform profile uses custom AWF-owned OpenCode agents and permissions; built-in Plan/Build
defaults are not assumed safe. The role-specialized profile uses Pi's narrow ephemeral/read-only
surface for Architect, the existing isolated OpenCode execution path for Coder, and Codex's
non-interactive read-only review surface for Reviewer.

## 3. Provider adapter contract

### 3.1 Complete 3 x 3 implementation

RC.2 must implement every Provider/Role cell:

| Role | Pi | OpenCode | Codex |
|---|---:|---:|---:|
| Architect | required | required | required |
| Coder | required | required | required |
| Reviewer | required | required | required |

Implementation must compose three Provider Drivers with three Role Policies, not create nine copied
workflow engines.

Provider Drivers own only:

- executable and structured argv;
- model flag and provider-native input attachment;
- fresh/ephemeral session choice;
- permission/sandbox/tool selection;
- stdout/event/final-result capture;
- provider exit observation and bounded diagnostics.

Role Policies own only:

- Architect read-only semantic decision and TaskCard assembly input;
- Coder isolated writable workspace with no trusted Git/merge authority;
- Reviewer exact-head read-only inspection and strict ReviewReport output.

Workflow, TaskCard, Git/PR, retry/replacement, merge, checkpoint, outbox/inbox and ACK authority stay
outside Provider Drivers.

### 3.2 Mature implementation rule

Before changing a Provider Driver, the TaskCard must compare:

1. the provider's current official CLI/SDK/RPC documentation;
2. the existing AWF adapter and real retained failures;
3. mature open-source integrations such as agtx where relevant;
4. provider permissions, sandbox, session and final-output contracts.

The implementation report records `reuse`, `adapt` or `reject` for each candidate. Do not copy
session-as-truth, ambiguous `--last`/`--continue`, yolo permissions, provider-owned Git authority or
another workflow engine. Do not build a generic provider framework until repeated real adapters
demonstrate the same missing boundary.

### 3.3 Architect semantic output

All three Architect providers use one closed semantic payload, not provider-authored protocol
Markdown. The current OpenCode candidate's seven fields are the starting contract:

```text
task_id
objective
scope
change_paths
constraints
acceptance_criteria
verification_commands
```

Trusted AWF code injects frozen Plan/main/repository/base/branch facts, roles, models, artifact paths,
reviewer selection and postflight contracts, then calls the existing canonical validator and
create-only persistence boundary. Provider-native structured output may enforce the semantic shape,
but it cannot inject authority facts or replace canonical validation.

One TaskCard is one bounded independently reviewable/mergeable change. It is executable without chat
history, does not pre-design future cards, does not expand the Plan and leaves tactical implementation
decisions to Coder unless the Plan or safety contract requires them.

### 3.4 Evidence and support claims

Each of the nine cells must pass deterministic conformance covering argv, inputs, environment,
permissions, workspace, output, artifact and failure/no-replay behavior. Each cell not exercised by
the two complete topology E2Es also receives one fresh real CLI/model invocation smoke; this is not a
business milestone and makes no cross-machine completion claim.

README may show the complete 3 x 3 support matrix only after:

```text
implementation
-> deterministic conformance
-> required real invocation smoke or topology E2E
-> independent review
-> CI
-> merge to main
```

The two official profiles are separately labelled as complete real-machine topology acceptances.
`r4-final-candidate` is implementation/evidence input only. It must not be merged wholesale or
claimed as support. Bounded changes are transplanted onto fresh main after current package/topology
boundaries, then revalidated. R1-R3 remain failed; a fresh acceptance identity is required.

## 4. Agent-native application and status contract

### 4.1 MCP facade

MCP is an RC.2 product entry, not a workflow engine. Its stdio adapter calls the same installed
application/facade semantics as CLI and owns no Workflow, TaskCard, merge, recovery or Agent Bus
transport state.

Required tools include:

```text
start_plan
get_status
doctor
stop
deinit
continue_after_approval
authorize_replacement
```

The Human normally does not see these names. `start_plan` and `get_status` are internal Agent calls
behind natural-language requests. Mutating tools require the corresponding explicit Human intent and
must validate current allowed actions before mutation. No MCP tool exposes ACK, requeue, replay,
checkpoint editing, arbitrary merge or raw Agent Bus operations.

### 4.2 Shared projection

CLI and MCP use one pure read-only projection:

```json
{
  "current_state": "...",
  "current_card": {},
  "last_completion": {},
  "roles": {},
  "blocker": {},
  "next_safe_action": "...",
  "allowed_actions": []
}
```

Default Human output answers:

- where the run is;
- which card is current;
- what last completed;
- what is blocking;
- what is safe next.

`--explain` adds internal causal facts. Unknown or conflicting authority projects only inspect/stop;
status never repairs, discovers by mutation or advances a run.

### 4.3 Human approval state

When GitHub branch protection requires approval, AWF enters nonterminal
`WAITING_FOR_HUMAN_APPROVAL`. It records exact PR/base/head/check facts and asks the Human to approve
that head. After the Human says continue, the Agent calls `continue_after_approval`; AWF re-observes
the exact tuple, required approval, CI and mergeability before trusted merge. It never bypasses
branch protection or accepts approval for a different head.

## 5. Recovery and Plan evolution

### 5.1 Durable boundaries

Provider interruption is classified as:

```text
A. provider not started
   -> same delivery may continue once

B. exact zero-exit result and workspace evidence durable
   -> skip provider and continue from validation/postflight

C. provider started but result cannot be proved
   -> BLOCKED_AMBIGUOUS; no automatic replay

D. Git/PR/outbox/merge effect uncertain
   -> re-observe the exact external fact; do not repeat the effect
```

### 5.2 Human-authorized replacement

For C, a Human may authorize a new replacement delivery for the same frozen TaskCard only when AWF
proves:

- the old exact provider process is terminated;
- no unexplained Git, PR, merge or outgoing effect exists;
- old checkpoint/evidence remains immutable;
- replacement has a fresh delivery/invocation identity and explicit lineage;
- attempt/rework capacity is not silently reset;
- role/tool/model/TaskCard/base/workspace authority has not drifted.

If any condition is unknown, replacement is denied and the run stays BLOCKED. Provider session
history is never authority.

### 5.3 Plan changes

An active Plan is never hot-updated. To revise scope:

```text
stop new-card creation
-> converge at a safe boundary
-> close old PlanRun as SUPERSEDED or BLOCKED
-> preserve CompletedCardFacts and failures
-> Human commits revised Markdown Plan
-> start a new PlanRun from exact latest main
```

The new Architect sees repository truth, not a rewritten old PlanRun.

## 6. Lifecycle and acceptance hygiene

### 6.1 Persistent versus disposable profiles

Profiles created by normal user `awf init` are persistent. `stop` ends exact listeners but retains
their installation for later start. A Human-requested `deinit` stops and uninstalls current-project,
current-machine exact profiles and removes local bindings.

Profiles created by formal acceptance are disposable. After evidence freeze, every PASS, FAIL,
BLOCKED or exception path must execute exact closeout. Failed business/provider evidence remains;
native process installations do not.

### 6.2 `deinit` boundary

`deinit` removes:

- exact current-project/current-machine listeners;
- native manager definitions;
- installed profile snapshots and registry aliases;
- local machine binding;
- AWF-generated role workspaces only when exact, clean and inactive.

It preserves:

- committed `.awf/project.yaml`;
- Plans and CompletedCardFacts;
- Run state, checkpoints, outbox/inbox;
- logs and Implementation/Review artifacts;
- retained failure evidence.

Dirty, identity-drifted or active workspaces make deinit refuse with one exact blocker. There is no
wildcard/force kill or task-name cleanup.

### 6.3 Run-owned lifecycle manifest

Each acceptance run persists a credential-free manifest of every created profile, digest, native
manager and manager ID. Closeout uses only this manifest:

```text
freeze evidence
-> stop new dispatch
-> observe scoped queues
-> graceful exact listener stop
-> verify process/lease absence
-> uninstall every run-owned profile
-> verify native definition/install record/registry absence
-> preserve logs, run state and failed evidence
```

Unknown identity yields `CLEANUP_BLOCKED`; it does not authorize wildcard deletion. RC acceptance
cannot pass while a run-owned manager definition remains.

### 6.4 Windows zero-popup requirement

Current main creates one InteractiveToken Task Scheduler action per profile, repeats every minute and
directly starts console `python.exe`. Historical acceptance tasks produced visible CMD windows and
were not automatically uninstalled. This is an RC.2 blocker.

The Task Scheduler action and every reconciler/listener descendant must run with no visible console
while preserving current-user credentials, logs, exact process creation identity and exact stop.
The first bounded candidate is the installed venv's `pythonw.exe` plus Windows
`CREATE_NO_WINDOW` for console descendants. PowerShell `-WindowStyle Hidden`, VBS/WScript wrappers,
task-name wildcard deletion and Task Scheduler UI-hidden flags are rejected as the authority or
window-suppression boundary. A tiny GUI-subsystem launcher is considered only if the smaller
candidate cannot preserve exact-stop semantics.

Real acceptance observes multiple periodic triggers under the logged-in console user and proves zero
visible windows, one exact listener, append-only logs, restart, stop and uninstall convergence.

### 7.1 Agent-native MCP facade

- **Current AWF capability:** an initiating Agent can run the Plan CLI over the existing application
  path.
- **Actual gap:** Human intent still leaks CLI flags and there is no shared structured Agent response.
- **Product benefit:** the Human authorizes in natural language while the Agent invokes one stable
  product tool boundary.
- **Golden Path impact:** direct; Agent-native invocation is now the normal product entry.
- **Implementation cost/risk:** medium; protocol and authorization mistakes could create a second
  workflow authority.
- **Authority/security impact:** the facade must remain stateless over the installed application and
  may expose only current allowed actions.
- **Recommendation:** RC.2.
- **Minimal viable shape:** the tools in section 4.1, one shared projection and one real Human -> Agent
  -> MCP -> existing workflow acceptance.

### 7.2 Architect / TaskCard decomposition discipline

- **Current AWF capability:** serial one-card generation and fresh-main continuation already exist.
- **Actual gap:** provider-authored full protocol Markdown is fragile, and task granularity/tactical
  freedom are not one shared policy.
- **Product benefit:** fewer invalid or over-broad cards without a new schema.
- **Golden Path impact:** direct Architect reliability improvement.
- **Implementation cost/risk:** low to medium; semantic assembly must not become TaskCard authority.
- **Authority/security impact:** trusted code injects authority; canonical validation remains final.
- **Recommendation:** RC.2.
- **Minimal viable shape:** the seven-field semantic payload, trusted assembly and the bounded
  decomposition paragraph in section 3.3.

### 7.3 Explicit allowed-actions projection

- **Current AWF capability:** DecisionOutcome, next-action, lifecycle and blocker facts already exist
  in several stores/views.
- **Actual gap:** Humans and Agents must join them mentally and can guess an unsafe mutation.
- **Product benefit:** one understandable state and one conservative next action.
- **Golden Path impact:** direct observability, recovery and approval requirement.
- **Implementation cost/risk:** medium to high because a false allowed action changes authority.
- **Authority/security impact:** pure read-only join; conflict collapses to inspect/stop.
- **Recommendation:** RC.2.
- **Minimal viable shape:** section 4.2 shared projection used by CLI and MCP mutation gates.

### 7.4 Provider-native session resume

- **Current AWF capability:** durable artifact/checkpoint continuation without session authority.
- **Actual gap:** exact provider session identity is not bound across every tool/role.
- **Product benefit:** potential latency/context optimization after safe interruptions.
- **Golden Path impact:** not required for safe stop, exact result continuation or Human-authorized
  replacement.
- **Implementation cost/risk:** high and provider-specific; ambiguous `--last` can replay the wrong
  conversation.
- **Authority/security impact:** session history can only be an optimization under exact invocation,
  workspace and artifact truth.
- **Recommendation:** backlog.
- **Minimal viable shape if later adopted:** exact provider session ID frozen before launch and
  revalidated; never implicit last-session lookup.

### 7.5 Benchmark / evaluation

- **Current AWF capability:** dogfood evidence records real cards, invocations, rework, review, CI,
  merge and retained failures.
- **Actual gap:** no normalized cross-release completion/cost/time/review-catch dataset.
- **Product benefit:** regression and provider/topology comparison after the product contract is
  stable.
- **Golden Path impact:** not an RC.2 functional blocker.
- **Implementation cost/risk:** medium to high if it grows into infrastructure before two accepted
  topologies exist.
- **Authority/security impact:** evidence-only; benchmark results never authorize workflow state.
- **Recommendation:** immediate post-RC.2.
- **Minimal viable shape:** normalize Phase 5 evidence before any general benchmark harness.

### 7.6 First-run auto detection

- **Current AWF capability:** local Git/GitHub/Bus/tool/version/profile/listener discovery.
- **Actual gap:** no tracked project topology, and local facts cannot authorize dynamic cross-machine
  selection.
- **Product benefit:** low-friction init without role drift.
- **Golden Path impact:** direct machine-ready and MCP-start prerequisite.
- **Implementation cost/risk:** low when limited to local facts; high if turned into an online
  registry/router.
- **Authority/security impact:** detection validates project intent; it never chooses a different
  online role.
- **Recommendation:** RC.2.
- **Minimal viable shape:** section 2 project file plus local discovery and Deep route proof.

## 8. RC.2 Definition of Done

RC.2 may be tagged only when all are true:

1. README, architecture and default help explain one product and one Golden Path.
2. A tracked credential-free project topology is generated, committed and validated.
3. Local init/doctor/deinit is understandable and exact on macOS and Windows.
4. The wheel runs outside a source checkout; production operations import as a formal package
   without runtime `sys.path` mutation.
5. All nine Provider/Role cells are implemented and pass deterministic conformance.
6. Cells outside the two topology E2Es pass fresh real CLI/model invocation smoke.
7. Full support claims appear only after review/CI/main merge; R1-R3 remain failures.
8. The initiating Agent starts an approved committed Markdown Plan through MCP without Human CLI
   parameters.
9. Human-free TaskCard creation uses closed semantic output plus trusted assembly and the canonical
   validator.
10. CLI/MCP status answers state, current card, last completion, blocker and next safe action without
    mutation.
11. Both official topologies complete a clean-installed real at-least-two-card milestone with exact
    review, CI, merge, latest-main continuation and MILESTONE_COMPLETE.
12. One real branch-protected flow enters WAITING_FOR_HUMAN_APPROVAL and continues only after exact
    Human approval.
13. Coder and Reviewer kill acceptances prove safe stop, visible effects and no internal-state edits.
14. One ambiguous provider case completes a Human-authorized, correctly linked replacement or
    truthfully remains BLOCKED.
15. Acceptance profiles automatically stop/uninstall on PASS and failure while preserving evidence.
16. Windows periodic reconciliation produces zero visible CMD/console windows and leaves no
    run-owned Scheduled Task after closeout.
17. User `deinit` removes exact native/profile/workspace bindings only under the frozen boundary.
18. Exact SHA, credential isolation, independent review, CI/merge authority, no-replay and ACK
    ordering remain unchanged.

Agent Bus and selected Agent Tools may be assumed installed and authenticated. An offline/no-Bus demo
is not required.
